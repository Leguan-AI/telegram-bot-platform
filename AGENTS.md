## Test-harness safety rules

1. Test scripts run against the shared database identified by `ADMIN_DATABASE_URL` / `DATABASE_URL`. Assume that database is **production**.
2. Test scripts must never `drop`, `truncate`, or revert schema on real tables. If a harness genuinely requires destructive DDL, it must be gated behind an explicit opt-in env flag (e.g. `ALLOW_DESTRUCTIVE_TEST_DDL=1`) and must fail fast with a clear message when the flag is absent.
3. Fail-injection via temporary constraints must use `not valid` (never validate existing rows) and the corresponding `drop constraint if exists` must appear at the **top of the `finally` block**, in addition to any in-body cleanup.
4. Row cleanup (setup and teardown) must target fixture UUIDs only — never unscoped deletes.
5. Harnesses may re-apply a migration file only if that migration is idempotent (`if not exists` / `create or replace` / `drop policy if exists` throughout).
6. New or modified test scripts must pass `npm run check:scripts`.
7. Harness-applied migrations bypass the Supabase migration ledger (`supabase_migrations.schema_migrations`): `sql.unsafe(migrationSql)` executes DDL against the real database without recording it, so `supabase migration list` will show the migration as missing on remote even though the schema exists. Migrations reach the remote database only via `supabase db push`, run by the operator **before** the harness's first execution — the harness re-apply is a convenience no-op for repeat runs, never the deployment mechanism. If a harness has applied a migration ahead of push, reconcile with `supabase db push` (safe because rule 5 requires harness-applied migrations to be idempotent; the `already exists, skipping` notices double as an idempotency proof) and verify with `supabase migration list`. `supabase migration repair --status applied <version>` is the fallback only if the migration somehow is not idempotent.
8. Verification plans and harness code must never invoke `supabase db push`, `supabase db reset`, `supabase migration repair`, or any other command that writes to the remote migration ledger (`supabase_migrations.schema_migrations`). Migrations reach the remote ledger only as a deliberate, separate act — never as a step inside a harness run or an automated checklist, regardless of how safe an individual migration is. This is distinct from rule 7: a harness is permitted to re-apply a migration's raw DDL via `sql.unsafe(migrationSql)` for test convenience (ledger-blind, reconciled later), but it must never call the CLI push/reset/repair commands themselves, which write to the ledger directly. If a verification plan lists `supabase db push` as a step, that step belongs outside the harness — remove it from any automated checklist.

   **Who may push (amended 2026-10-22, by David).** An agent may run `npm run db:push` only when **the operator has explicitly approved that specific push in their own words**: the migration file(s) and the target (production, or a named Supabase branch or staging project). Approval relayed by another agent, implied by a task, or given for an earlier migration does not count. Before pushing, the agent must (a) run `supabase db push --dry-run` against the named target and show the operator the pending list, (b) state a rollback for each migration, and (c) get a **separate explicit OK** for any migration that drops or renames objects, changes or deletes data, disables or loosens RLS, or widens grants. Production pushes happen **before** the PR merges, because Vercel deploys on merge. After pushing, the agent records what was pushed (versions, target, time, who approved) in the PR and shows `supabase migration list`. Pushing from CI, from a harness, or as an unrequested step of a larger task stays forbidden. `db reset` and `migration repair` stay operator-only, by hand.

   `scripts/db-remote.sh` carries as much of this as a script can: it refuses when `CI` is set, requires `SUPABASE_PROJECT_REF` with no default (so an unset variable can never mean production), requires `CONFIRM_PROD=1` when that ref is the production project, requires `ALLOW_NONINTERACTIVE_DB_PUSH=1` outside an interactive terminal, and always runs `--dry-run` first and prints it. The judgement calls — whether the approval was explicit, whether the migration is destructive, what the rollback is — are the agent's to make and cannot be delegated to the script.

## Migrations: grants for new tables, views and functions

Since 2026-10-30 Supabase no longer auto-grants new `public` tables, views or sequences to `anon`/`authenticated`/`service_role`, and `20261029000000_api_surface_lockdown.sql` already removed those defaults here (and the `PUBLIC`/`anon`/`authenticated` default `EXECUTE` on new functions). A missing grant fails with `42501` before RLS runs. Full guidance: `DEPLOYMENT.md`, "Database grants: new tables (and views) need explicit grants" and the subsection before it for functions.

- Every migration that creates a table, view or function states its grants **in the same file**; never rely on defaults. Use `revoke`/`grant` per role, never `grant all`.
- Decide the access path first. Bot only: no `anon`/`authenticated` grant (note `bot_service` is auto-granted full DML on new tables by the init defaults; revoke and re-grant narrower if it needs less). Dashboard: prefer a `SECURITY DEFINER` RPC with `grant execute ... to authenticated`; use a direct table grant to `authenticated` only together with `enable row level security` and policies, and only for the operations `/manage` issues.
- Never grant to `anon` or `PUBLIC` (nothing in `/manage` is public); never grant `truncate`, `references`, `trigger`; nothing to `service_role` (the app does not use it).
- A grant without a policy returns no rows, a policy without a grant is unreachable; the new migration needs both for a browser-facing table.
- Update `scripts/test-api-surface-lockdown.ts` (the expected `authenticated` tables and the `KEPT` function list) when you add a browser-facing table or RPC, and run it against the target database.
- Do not edit an applied migration. Applying migrations to a remote database is the operator's act (see the test-harness rules above).
